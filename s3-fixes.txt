FIX 1 — Boot failure after erase_flash (wrong FQBN / 4 MB vs 32 MB flash mismatch)
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  Device outputs ROM boot messages up to "entry 0x403c88b8" then goes completely
  silent. Display stays blank. Crash/no-boot loop or silent hang.

Root cause:
  The board has 32 MB external flash, but all prior builds used the generic FQBN
  esp32:esp32:esp32s3 which defaults to 4 MB flash and generates a 4 MB merged.bin.
  The second-stage bootloader header encoded "4 MB" as the flash size. The bootloader
  ran in IRAM but its flash-controller configuration (expecting a 4 MB chip behind
  the SPI bus) was wrong for the 32 MB chip, causing a silent hang immediately after
  entry before any UART output could be produced.

  Additionally, erasing the full flash (esptool erase_flash) destroyed the original
  working bootloader. Subsequent arduino-cli upload commands only write the app binary
  (0x10000) and do NOT restore the bootloader (0x0) or partition table (0x8000).

Fix:
  1. Compile with the board-specific FQBN (see above).
  2. Flash the full 32 MB merged.bin via esptool (see above).
  3. All future app-only uploads use:
       arduino-cli upload --fqbn "esp32:esp32:waveshare_esp32_s3_touch_amoled_206" -p /dev/ttyACM0 .

FIX 2 — JPEG smearing on right edge (MCU stride mismatch in jpegDraw)
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  Right edge of every weather frame and terrain snapshot smears horizontally
  across the entire width of the image. First appeared when DISP_W was changed
  from 320 to 410.

Root cause:
  JPEGDEC returns partial last MCU columns via pDraw->iWidthUsed < pDraw->iWidth
  when the image width is not a multiple of 16. Example: 410 px wide image →
  last MCU column at x=400 has iWidthUsed=10, iWidth=16. Calling
  pushImage(x, y, iWidthUsed, height, pixels) tells LovyanGFX that the row
  stride is iWidthUsed (10), but the pixel buffer actually has stride iWidth (16).
  Every row after the first reads from the wrong offset → smearing.
  MCU-aligned widths (320 = 20×16, 176 = 11×16) never trigger partial columns
  so the bug is invisible at those sizes.

Fix (in jpegDraw callback):
  if (drawW == blockW) {
      g_drawTarget->pushImage(x0, y0, blockW, pDraw->iHeight, (uint16_t*)pDraw->pPixels);
  } else {
      // Partial last column: stride in buffer is blockW, not drawW.
      // Write row-by-row using the correct stride offset.
      uint16_t* src = (uint16_t*)pDraw->pPixels;
      for (int row = 0; row < pDraw->iHeight; row++) {
          g_drawTarget->pushImage(x0, y0 + row, drawW, 1, src + row * blockW);
      }
  }
  (where blockW = pDraw->iWidth, drawW = pDraw->iWidthUsed > 0 ? pDraw->iWidthUsed : blockW)

Rule: always keep DISP_W and DISP_H as multiples of 16 (MCU-aligned) to avoid
partial columns entirely. Current values: 320×176.

FIX 5 — Animation only shows first ~70% of frame timeline
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  Animation plays for 10 s but only shows frames from "24 hours ago" to "11 hours
  ago", then jumps to "2 hours ago" (the latest frame hold). The last ~30% of the
  24-hour weather timeline is never shown.

Root cause:
  The slot loop used slot number to select frames: srcPos = slot * validCount / slots.
  With slots=100, validCount=109, and frames taking ~130 ms each, only ~77 slots
  completed before the 10-second break. Slot 77 → frame 84 of 109 = 77% of timeline.
  The break fired having shown only the first 77% of frames.

Fix:
  Replace the slot-based loop with a time-based loop. At each iteration, map the
  ACTUAL elapsed time to a frame position:
    srcPos = elapsed * validCount / animationDurationMs
  This way, even if only 77 iterations complete, they are spread across 0–100% of
  the frame timeline. A pre-freeze window (last 2×targetFrameDelayMs of animation)
  shows the JPEG-quality newest frame to seed the hold phase.

  Key change in loop():
    for (;;) {
        uint32_t elapsed = millis() - loopStartMs;
        if (elapsed >= animationDurationMs) break;
        uint32_t srcPos = (uint32_t)(((uint64_t)elapsed * (uint64_t)validCount)
                                     / animationDurationMs);
        if (srcPos >= (uint32_t)validCount) srcPos = (uint32_t)validCount - 1U;
        uint32_t remaining = animationDurationMs - elapsed;
        if (remaining <= targetFrameDelayMs * 2U + 50U) {
            // pre-freeze: show JPEG newest, pad to deadline, break
        } else {
            showFrame(validIdx[srcPos]);
        }
    }

FIX 6 — WiFi/SSL connection refused during frame download (OOM in internal DRAM)
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  All 144 frame downloads fail with HTTP code -1 ("connection refused").
  Free heap at download time: ~51 KB. Device shows "No frames" after boot.

Root cause:
  presentScaledBuf() declared a static chunk buffer in BSS:
    static uint16_t s_chunkBuf[32 * 410];  // 26,240 bytes internal DRAM
  Raising CHUNK_ROWS from 8→32 added ~20 KB to global BSS, reducing internal
  heap from ~71 KB to ~51 KB. WiFiClientSecure (mbedTLS) needs ~35–40 KB of
  contiguous internal DRAM for the SSL handshake buffer. At 51 KB free, the
  allocation fails and the connection is reported as "refused".

Fix:
  Move s_chunkBuf to PSRAM (lazy-allocated on first present call) and restore
  CHUNK_ROWS to 8. PSRAM is safe here because the QSPI display driver reads
  data sequentially, not via DMA.

    static const int CHUNK_ROWS = 8;
    static uint16_t* s_chunkBuf = nullptr;
    if (!s_chunkBuf)
        s_chunkBuf = (uint16_t*)heap_caps_malloc(CHUNK_ROWS * SCALED_W * 2U, MALLOC_CAP_SPIRAM);

  Result: global BSS dropped from 229 KB → 203 KB (62% of 327 KB).
  Internal heap during download: ~77 KB — sufficient for SSL.

Rule: keep all large static display buffers in PSRAM. Internal DRAM must remain
free for WiFi stack, mbedTLS SSL (~35–40 KB), and HTTPClient/String allocations.

FIX 7 — "No frames" after SDMMC switch (SD_ROOT path prefix double-prepend)
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  Device downloads 144 frames but saved=0 every run. buildRawPlaybackCache shows
  "SKIP: no frames", then "Download done!", then main loop shows "No frames".

Root cause:
  The Arduino ESP32 VFSImpl (FS/vfs_api.cpp) internally prepends _mountpoint to
  every path passed to open(), mkdir(), remove(), rename(), rmdir(). When SD_MMC
  is mounted at "/sdcard", passing "/sdcard/frames/f000.jpg" to SD_MMC.open()
  produces the VFS call fopen("/sdcard/sdcard/frames/f000.jpg"). The VFS layer
  strips "/sdcard", leaving FatFS with "/sdcard/frames/f000.jpg" — which requires
  a directory named "sdcard" at the SD card root. That directory doesn't exist,
  so every file open fails silently (returns null), every write returns 0, and
  saved=0 after the download loop.

  The begin("/sdcard") mount point is ONLY for VFS registration. File paths passed
  to all other API calls must be card-root-relative (e.g. "/frames/f000.jpg"),
  NOT prefixed with the mount point.

Fix:
  #define SD_ROOT ""   // empty — VFSImpl adds "/sdcard" internally
  SD_MMC.begin("/sdcard", ...)  // mount point used only here

  With SD_ROOT="", FRAMES_DIR="/frames", META_FILE="/frames/meta.txt", etc.
  VFSImpl prepends "/sdcard" → fopen("/sdcard/frames/f000.jpg") → correct.

Rule: for SD_MMC (mounted at "/sdcard"), paths passed to open/mkdir/remove/rename
must NOT include the "/sdcard" prefix. The mount point is used only in begin().
This matches the LCD_147 board behavior and Arduino ESP32 SD_MMC examples.

FIX 9 — WiFi link drops after a few seconds of successful data transfer
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  Device associates and transfers data normally for 3–5 seconds, then the
  connection drops silently. No error is reported. Reconnect attempts succeed
  briefly before dropping again in the same pattern.

Root cause:
  The CPU-intensive processing task (decode + scale + display push, ~20–30 ms)
  was pinned to Core 0. On ESP32-S3, the WiFi stack runs its own internal
  FreeRTOS tasks on Core 0 and requires regular CPU time to service beacons,
  association keepalives, and the MAC TX/RX queues. With a long-running task
  monopolising Core 0, the WiFi driver tasks were starved. The link held long
  enough for initial association, then collapsed once keepalive frames went
  unserviced. The symptom resembles a signal problem but is purely a CPU
  scheduling issue.

Fix:
  Reassign tasks so each core does what it is suited for:

    Core 0 — all network I/O and radio-adjacent work, co-located with the
             WiFi stack. Add an explicit yield (vTaskDelay(1)) when idle so
             the WiFi driver tasks get CPU time between bursts.

    Core 1 — all CPU-intensive processing (decode, transform, display push).
             Fully isolated from the WiFi stack; long blocking cycles here
             have no effect on the link.

  Park loop() permanently with vTaskDelay(portMAX_DELAY) so it never
  competes with either explicit task.

Rule: on ESP32-S3, never pin CPU-intensive tasks to Core 0. The WiFi stack
lives there and requires cooperative scheduling to maintain any active
association. All heavy processing belongs on Core 1.

FIX 10 — Display stays blank, gfx->begin() returns false or hangs
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  Sketch compiles and uploads cleanly. Display remains black. gfx->begin()
  returns false or the device hangs silently at that call. Nothing appears
  on serial.

Root cause:
  The AMOLED panel is gated behind a PMIC power-enable pin (AMOLED_PWR_EN)
  that defaults LOW at boot, cutting power to the display. Calling gfx->begin()
  before asserting the pin attempts to initialise a de-powered device over QSPI
  and either fails silently or hangs indefinitely. No error is surfaced because
  the display controller is not responding at all.

Fix:
  Assert AMOLED_PWR_EN HIGH before any display call and allow 50 ms for the
  panel to reach stable supply voltage before begin():

    pinMode(AMOLED_PWR_EN, OUTPUT);
    digitalWrite(AMOLED_PWR_EN, HIGH);
    delay(50);
    gfx->begin();

Rule: AMOLED_PWR_EN must be the first display-related operation in setup().
No display call is valid before the pin is HIGH and the delay has elapsed.
Omitting this step produces a blank display with no diagnostic output —
it is indistinguishable from a wiring fault or a failed flash.

       QMI8658_INT1  = 21
     So GPIO21 is not a free user GPIO on this board.

Rules that follow from this:
  Rule A: On this board, SD must use 1-bit SD_MMC unless there is a deliberate,
  fully reworked reason to do otherwise. Do not route the weather app through
  SPI SD on the AMOLED-2.06 board.

  Rule B: Do not manually wiggle `SDMMC_CS` (GPIO17) during normal 1-bit SD_MMC
  mount. The vendor example leaves it alone and mounts with only CLK/CMD/D0.
  If mount fails, fix filesystem/card state first; do not "help" it by forcing
  GPIO17 unless there is a proven hardware reason.

  Rule C: For Arduino_GFX on this board, the known-good panel configuration is:
    `Arduino_ESP32QSPI` + `Arduino_CO5300`
    rotation = 0
    width    = 410
    height   = 502
    col_offset1 = 22
  Any alternative controller path should be treated as a regression risk.

  Rule D: Reserve GPIO13 (`AMOLED_TE`). It is a real TE pin on this board.
  Even if unused today, do not repurpose it casually; it is the one hardware
  pin available for future display-sync / tear mitigation work.

  Rule E: Reserve GPIO21 for panel power unless IMU interrupt handling is
  intentionally designed around that shared pin. Pulling it LOW or repurposing
  it casually can blank the display.

  Rule F: Use the core's board identity macros when possible:
    `WAVESHARE_ESP32_S3_TOUCH_AMOLED_206`
    `BOARD_HAS_SD_SDMMC`
  They are concrete compile-time signals already provided by the platform and
  are safer than ad-hoc custom board detection.

  Rule G: Touch, RTC, IMU, and PMU all sit on the same I2C wiring domain on
  this board. Keep one shared `Wire.begin(15, 14)` model. Do not treat those
  peripherals as if they are on separate buses.

FIX 12 — Freeze frame / zoom snapshots show black MCU blocks
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  Animation may look mostly acceptable, but the freeze frame and the zoom
  stages show obvious black rectangular blocks or band-like black gaps. The
  defect is much more visible in the hold/zoom path than in normal playback.

Root cause:
  There were two separate issues in the S3 build:

  1. `buildRawPlaybackCache()` was too permissive. It only rejected total decode
     failure and fully black frames before baking frames into `stream.raw`.
     That allowed partially bad frames to be accepted into the cached playback
     stream even though the stricter zoom-raw builder would have rejected them.

  2. The pre-freeze path preferred a fresh live JPEG decode of the newest frame
     right before the hold state. That re-entered the fragile decode path at the
     exact moment the image becomes most visible.

  3. The existing hold-frame block detector only caught isolated single 16×16
     zero-MCU holes. It missed wider zero-band failures.

Fix:
  Make the raw-cache build use the same guard class as the zoom snapshot path,
  strengthen the zero-band detector, and prefer the cached frame at freeze:

    - bump `RAW_CACHE_VERSION` to force raw-cache rebuild
    - in `buildRawPlaybackCache()`, reject frames before writing `stream.raw` if:
        `spriteLooksNearlyBlack()`
        `spriteLooksPartialDecode()`
        `spriteLooksHorizontallyCorrupted()`
        `spriteLooksVerticallyCorrupted()`
        `spriteLooksHoldFrameBlockCorrupted()`
      return true
    - keep bad slots zeroed and let the existing nearest-valid backfill logic
      replace them later
    - after raw-cache rebuild, force local rebuild of:
        `vz1.raw`
        `vz2.raw`
        `vz3.raw`
      so zoom snapshots are regenerated under the stricter guards
    - expand `spriteLooksHoldFrameBlockCorrupted()` to also catch:
        near-full-width interior zero rows
        two consecutive interior rows with heavy zero-block counts
      while preserving the original isolated zero-block check
    - in the pre-freeze branch of `loop()`, use:
        `showFrame(newestIdx)` first
      and only fall back to:
        `showZoomSnapshotFrame(newestJpegPath, newestIdx)`
      if the cached frame cannot be shown

Why this works:
  The visible artifact was not only a display-path problem. Part of it was being
  accepted into the cached image path itself. Once a weakly validated frame was
  baked into `stream.raw`, the hold and zoom stages could repeatedly surface it.
  Tightening cache acceptance removes bad candidates earlier, and preferring the
  prevalidated cached frame at freeze avoids a last-second live decode glitch.

Result:
  This change materially reduced or eliminated the black-block artifact in the
  freeze frame and zoom snapshots on the S3 AMOLED build, without changing the
  board bring-up path, SD transport, or display driver stack.

Rule:
  On this S3 build, freeze/zoom quality fixes should be applied at the
  decode/cache acceptance layer first. Do not assume every visible block is a
  display-transfer problem; reject bad frames before they are baked into cache.

FIX 13 — Zoom snapshots disappear after ZOOM1 / deeper zoom stages missing
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  The freeze-frame locator cue can display, ZOOM1 may appear, but ZOOM2/ZOOM3
  can disappear and the sequence falls through to the freeze/clock path.

Root cause:
  The S3 build was requesting supersampled 2x zoom JPEGs for all three zoom
  stages. On deeper zoom crops, the 2x request is the most likely to fail due
  to JPEG size/validation limits, which leaves the later zoom files absent or
  stale. Once the cached zoom set is bad, the UI can keep reusing that broken
  set until zoom metadata is invalidated.

Fix:
  Make zoom snapshot refresh use a controlled 2x → 1x fallback per stage, and
  force a zoom metadata bump so the broken cached set is replaced:

    - in `refreshZoomSnapshotsForLatestFrame()`, for each of ZOOM1/2/3:
        first try `installValidatedZoomSnapshotAtBbox(..., ZOOM_FETCH_W, ZOOM_FETCH_H)`
        if that fails, retry once with `(..., DISP_W, DISP_H)`
    - log the fallback with:
        `zoom zN fallback 1x`
      so it is visible when a deeper stage could not sustain the 2x request
    - bump `ZOOM_META_VERSION` to force a one-time redownload of the zoom set
      after the logic changes, so stale bad `vz1/vz2/vz3` metadata is not reused

Why this works:
  The useful quality path is still preserved where it succeeds: zoom stages can
  use the sharper 2x source. But deeper stages no longer disappear just because
  the supersampled request fails for that particular crop. The fallback keeps
  all three zoom stages present instead of treating the 2x failure as fatal.

Result:
  The red bbox cue still works, and the full `ZOOM1 -> ZOOM2 -> ZOOM3` sequence
  returns. If a deeper stage cannot sustain the 2x fetch, it silently falls back
  to 1x instead of disappearing.

Rule:
  On this S3 build, supersampled zoom requests must degrade gracefully. Never
  let a failed 2x zoom fetch remove an entire zoom stage when a 1x source can
  still preserve sequence continuity.

FIX 14 — Rolling cache no longer full-refreshes every boot due to dim.cfg loss
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  The S3 build could perform a full 144-frame redownload and full raw-cache
  rebuild on every boot, even when the device had just updated. `diag.txt`
  showed:

    `dim='' expected='320 176'`
    `DIM MISMATCH -> PURGE`

  That purge happened before rolling reuse logic had any chance to run.

Root cause:
  The frame-dimension guard in `setup()` uses `FRAME_DIM_FILE` (`/frames/dim.cfg`)
  to decide whether the on-SD cache matches the current logical frame size.
  During a full refresh, the cache directory could be purged and rebuilt, but
  the code was not recreating `dim.cfg` after a successful cache install.

  That created a persistent loop:

    - full refresh deletes `/frames/dim.cfg`
    - cache rebuild finishes, but `dim.cfg` is still missing
    - next boot sees `dim=''`
    - setup triggers `DIM MISMATCH -> PURGE`
    - cache is wiped again and rebuilt from scratch

Fix:
  Make the normal cache-install path always rewrite the current frame-dimension
  metadata whenever a valid cache is installed:

    - add `writeCurrentFrameDimMeta()`
    - call it from `installCacheState()` whenever `count > 0`
    - make `downloadFrames()` use `installCacheState(...)` instead of manually
      setting `frameCount` / `framesReady` / `meta.txt` only
    - log the write to `diag.txt` with:
        `cache-meta: dim write OK '320 176'`

Why this works:
  `dim.cfg` is part of the cache validity contract. If it is missing, the boot
  path assumes the cached JPEGs belong to a different frame size and purges them.
  Rewriting `dim.cfg` on every successful cache install makes the cache stable
  across boots, so rolling reuse can run instead of being pre-empted by an
  artificial dimension mismatch.

Result:
  The repeat purge loop is broken. After one successful cache build, subsequent
  boots can reuse the existing cache instead of immediately forcing a full
  redownload just because `dim.cfg` was absent.

Rule:
  Any code path that installs or rewrites the weather frame cache must also
  rewrite `FRAME_DIM_FILE`. `meta.txt` alone is not enough to preserve cache
  validity across boots.

FIX 15 — Cyan-corrupted cached JPGs no longer poison animation playback
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  A specific weather frame (for example `f078.jpg`) could keep showing the same
  cyan/white blocky corruption in animation even after multiple reboots.

  Inspection confirmed the corruption was already present in the cached `.jpg`
  file on SD, so the issue was not a display artifact and not a `stream.raw`
  timing artifact.

Root cause:
  The stronger semantic validator was protecting new downloads and repair
  attempts, but a poisoned cached JPG could still survive in two ways:

    1. the `Cache current` fast paths could skip straight past the one-time
       full-cache repair pass, so old bad `fNNN.jpg` files were never revisited
    2. `buildRawPlaybackCache()` / rolling raw rebuilds still only used the old
       structural checks plus the simple cyan tile heuristic

  That meant a cached JPG that was structurally valid but semantically wrong
  could still be baked into `stream.raw` and keep reappearing in animation.

Fix:
  Apply the semantic outlier check to the raw-cache build itself, and make sure
  the one-time full-cache repair can actually run on cache-current boots:

    - in the `latest-current` and `exact-current` fast paths:
        call `validateAndRepairFullCacheIfNeeded(cacheCount)` before skipping
        if any repairs occur:
          rebuild raw immediately
          mark zoom snapshots stale
    - bump `CACHE_VALIDATE_VERSION` so stale `validate.meta` is invalidated once
    - in all raw-cache generation paths:
        `buildRawPlaybackCache()`
        `rebuildRawPlaybackCacheRolling()`
        `remapRawPlaybackCacheRolling()`
      call:
        `weatherFrameLooksSemanticOutlier(i, framePath, "...")`
      after decode and before writing the frame into `stream.raw`
    - if the frame is a semantic outlier:
        skip it exactly like a black/line/cyan structural failure
        do not bake it into `stream.raw`

Why this works:
  Even if a poisoned cached JPG is still sitting on SD, the animation path now
  has a second containment barrier: the raw builder refuses to promote that file
  into the playback stream. This breaks the visible symptom immediately, without
  requiring the JPG repair path to succeed first.

Result:
  The same cyan-corrupted cached frame no longer appears in animation after the
  raw cache rebuild, because the bad JPG is skipped during `stream.raw` build
  instead of being written into the playback cache.

Rule:
  Structural JPEG validity is not enough for weather frames. Any frame accepted
  into `stream.raw` must also pass the semantic outlier check, or it can poison
  playback even when the source `.jpg` is still cached on disk.

FIX 16 — Terrain layer vertical alignment matches the centered location pin
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  The terrain stage looked slightly north-shifted relative to the centered
  location pin and the preceding `ZOOM3` weather image. Visually, the pin looked
  too far south on the terrain layer.

Root cause:
  The terrain stage was using the same geographic bbox as `ZOOM3`, but it was
  being fetched through the short 2x raster path:

    - width: `640`
    - height: `344`

  That `344px` request decodes to only `172` real rows at half scale, and the
  remaining bottom rows were padded. The result was effectively:

    - top `172` rows of real terrain content
    - plus padded bottom rows

  That biases the visible terrain north even though the geographic center value
  is correct, so the fixed center pin appears too far south.

Fix:
  Keep zoom snapshots on the proven `344px` 2x path, but give terrain its own
  true full-height 2x fetch dimensions:

    - add:
        `TERRAIN_FETCH_W = DISP_W * 2`
        `TERRAIN_FETCH_H = DISP_H * 2`
    - use `TERRAIN_FETCH_W/H` for:
        day terrain download
        night terrain download
        terrain-stage radar download
    - leave `ZOOM_FETCH_W/H` unchanged for `ZOOM1/2/3`

Why this works:
  Terrain now gets a real `640x352` source raster, which half-scales to the full
  `320x176` logical terrain image with no missing bottom rows and no vertical
  padding bias. The terrain layer therefore stays centered on the same bbox as
  `ZOOM3`, and the centered location pin visually matches the terrain content.

Result:
  The terrain stage is no longer visibly north-shifted relative to the location
  pin, and the terrain transition aligns correctly with the centered `ZOOM3`
  target area.

Rule:
  `ZOOM3` and terrain may share the same geographic bbox, but they must also use
  a raster path that preserves the same effective vertical sampling if they are
  expected to align visually. For terrain, do not use the short `344px` 2x path.

FIX 17 — Terrain wipe/Radar stage no longer collapses when only one terrain layer downloads
─────────────────────────────────────────────────────────────────────────────────
Symptom:
  After sync, terrain wipe sometimes disappeared and radar status degraded to
  `Radar: n/a`. Logs showed:
    `terrain: pair fail d=0 n=1 keep=0/0`
  even though one of the two terrain sources had downloaded successfully.

Root cause:
  Terrain refresh logic treated day/night as an all-or-nothing pair. If one layer
  failed in that pass, the whole terrain stage was considered unusable, which
  blocked terrain composite generation and caused wipe/radar fallback behavior.

Fix:
  Relax terrain refresh to support partial success and self-heal the missing side:
    - accept whichever terrain layer downloaded successfully
    - keep prior usable copy if present
    - if only one side is available, copy it into the missing day/night slot so
      both expected files remain present for downstream code paths
    - only fail when neither side is available
  This keeps terrain assets usable and prevents wipe/radar stage collapse.

Result:
  Terrain wipe reliably runs again, and radar overlay path stays available even
  when one terrain source has a transient fetch failure.

Rule:
  Terrain stage must degrade gracefully on single-source failures; never gate the
  full terrain pipeline on strict same-pass day+night pair success.

## Fix: Partial GIBS composite ("black corner" freeze frame) — 2026-03-06

Problem:
  At the lag boundary (most recent available scan), GIBS sometimes serves a
  partial composite: the satellite was mid-scan when GIBS cached the response.
  The resulting 320×176 JPEG has a large black rectangle in one corner with
  normal satellite data in the rest. This frame:
    - Is a valid JPEG (passes magic check)
    - Passed the old 5500B minimum
    - Passes all pixel-level corruption checks
    - Is visually broken (black corner freeze frame visible to user)

  Empirical size data from fetch_frames.py + SD card sample:
    - Bad partial composite (f133.jpg, 18:00 UTC at sync time): 7265B
    - Same timestamp 5 hours later (GIBS finished compositing): 8084B
    - Smallest known valid frame in 144-frame window: 7333B
    - Largest valid frame: 12862B
    - Blank GIBS placeholder (already rejected): 614B

  The bad frame fell in the gap between 614B and 7333B, slipping past the old
  5500B threshold.

Fix:
  Raise MIN_WEATHER_JPEG_BYTES from 5500 to 7000 in esp32-LiveSat-s3.ino
  (line 4918). No other changes needed.

  The existing ±1 min probe loop in downloadFrames() (lines 7086-7122) already
  handles the retry automatically:
    - Attempt 0 (t+0s): returns 7265B partial → rejected (< 7000)
    - Attempt 1 (t-60s): requests previous cadence window → GIBS returns fully
      composited prior scan (~8000B) → accepted

  7000B chosen (not 7300B) to leave margin for valid frames that may be slightly
  smaller in different seasons/clear-sky conditions.

Result:
  Partial composite is rejected at download time. Probe falls back to the
  previous fully-composited scan. No black corner frames enter the animation.

Rule:
  If future data shows valid frames going below 7000B, lower to 6500B.
